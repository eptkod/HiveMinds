# Handoff: Agent Office Remake (Mac first, Windows later)

## Goal
Remake the "Agent Office" app (by Web Dev Cody, which Ethan uses today) as a personal tool with a much better UI. It is not for sale. Priorities, in order:

1. **Intuitive.** The existing 2D office view doesn't look or work intuitively to Ethan.
2. **Beautiful and lightweight.** Apple-style "Liquid Glass" look (translucent, blurred, rounded, layered) without being heavy on RAM/CPU.
3. **Feature parity** with Agent Office (see below).
4. **Simple GitHub connection** that someone with almost no GitHub knowledge can finish in a couple of clicks, so agents can make commits, PRs and releases.
5. **Works with the Claude Code CLI.**
6. **macOS first.** Windows build later, so don't pick tech that blocks that.

## Audit results (done 2026-10-19, from the installed app's source, v0.1.206)
Source: `~/.local/share/agent-office/versions/v0.1.206` (README plus built server code). Upstream repo: github.com/AgentSystemLabs/agent-office (MIT).

What Agent Office actually is:
- A **local Node server** (port 4600) with a **browser UI**. The main view is a **3D** office (three.js); `/lite` is a plain **2D list view** for phones and slow machines.
- **Floors = projects.** Each GitHub repo is a floor. Picking a repo clones it to `~/agent-office/projects/<owner>/<repo>`.
- **Workers at desks.** Hire a worker at a desk, choose the CLI (Claude Code, Codex, OpenCode, Grok, Muse, DeepSeek, Pi, Cursor), model and effort. Each runs in a real **pty terminal** (node-pty + xterm) that you can open and type into. Optional **own git worktree and branch** per worker.
- **Status via Claude Code hooks.** The app injects hooks (SessionStart, UserPromptSubmit, PreToolUse, Stop, Notification, PermissionRequest) that POST to the local server. This drives working / waiting-for-you / done, a red beacon plus alarm when a worker needs you, and the "N" key to jump to it.
- **Auto task names.** Claude Haiku (via the `claude` CLI) writes a short title and one-line summary of what each worker is doing.
- **Meeting room.** 2 to 5 workers, one pattern, a prompt, rounds. Patterns: Debate, Lead and team, Map-reduce, Red/blue, Review panel (posts a combined review on a PR). Meetings run in their own worktree, progress is checked by files each worker writes, and the output doc (e.g. `docs/decisions/<slug>.md`) is committed. Token and cost totals are shown. History of past meetings is kept.
- **Task queue.** GitHub issues or free-text tasks wait in order and auto-start as worktree workers when a desk frees up, up to a max.
- **GitHub boards.** Issues and PRs on cork boards: view, comment, label, assign, merge, close, hand an issue to a worker. A gong rings when a PR merges. "Send home on merge" option.
- **PRs.** One key pushes the worker's branch and opens a PR with an auto-drafted title and body. PRs a worker opens itself (`gh pr create`) are detected. Multi-repo tasks get linked PRs.
- **Agents managing agents.** An `agent-office` MCP server and `office-workers` CLI let agents list, hire, message and send home other workers.
- **Extras:** voice-to-text prompts, voice chat, text chat, screen share, shared whiteboard (Excalidraw), multi-user accounts, cloud deploy scripts, themed maps, plus decorative items (dog, arcade, cars, rooftop bar).
- **Not present:** creating **GitHub releases**. This is new work for us.

GitHub connection, as Agent Office does it:
- Everything goes through the **GitHub CLI (`gh`)**, which is required.
- First-run setup in the terminal offers to run `gh auth login`.
- The in-app "Sign in with GitHub" runs `gh auth login --web`, captures the one-time code, shows it with a link to github.com/login/device, and confirms the account with `gh api user`. Pasting a token is the fallback.
- The repo picker in the "elevator" lists your repos and clones the chosen one.

Meetings, fully working (2026-10-19, Ethan asked for meetings with a room like the Canvas):
- **How it runs.** A meeting is one ordinary interactive Claude Code session per seat (an `Agent` with `meetingID` set), all in one folder: the meeting's own worktree `<project>/.hiveminds/worktrees/meeting-<topic>-<id>` on branch `hive/meeting-…` (or the project folder if it isn't a git repo). ## UI direction
- **Look:** Apple Liquid Glass style: translucent panels, background blur, soft highlights, large corner radii, subtle motion, native-feeling window with a unified title bar.
- **Honest trade-off to decide early:**
  - *True* Liquid Glass is only available via native SwiftUI/AppKit on recent macOS. That gives the best look and lightest footprint on Mac but **no Windows build** from the same code.
  - A web-UI app (Tauri) can approximate it with `backdrop-filter`, translucent window vibrancy and careful styling. It looks close and keeps Windows possible.
- **Recommendation:** Tauri 2 + React + TypeScript + Tailwind, using the macOS vibrancy/window-effect APIs for the glass. It is light, cross-platform and fast to iterate. Revisit SwiftUI only if Ethan decides Mac-only is fine and wants the most authentic look.
- **Office view:** keep the "office" idea but make it clear at a glance. Ideas to test with Ethan: rooms as glass cards (Workspace, Meeting Room, Release Desk), agents as avatars with a clear status ring and a one-line "what I'm doing", click to open the agent's thread. Avoid a decorative map that makes people hunt for things. Show a simple list/board view as an alternative.
- Make the primary actions obvious: **New Agent**, **Start Meeting**, **Connect GitHub**, **New Release**.

## Suggested architecture
- **Shell:** Tauri 2 (Rust backend, web frontend).
- **Rust side:** spawn and manage `claude` processes (pty and headless), Keychain access, filesystem and git operations, local persistence.
- **Frontend:** React + TS, state in something small (Zustand), xterm.js for terminal panes.
- **Storage:** SQLite or JSON files in the app support directory for agents, meetings, transcripts and settings.
- **Events:** the Rust side streams CLI events to the UI over Tauri events.
